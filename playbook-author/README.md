# playbook-author

Turns a procedure described in plain language into a **Console-style playbook**, and saves it as a
**Playbook agent** (Agents list → *Playbooks*) that can be dragged onto a workflow canvas as a
Playbook node.

## What it produces

You describe a process the way you would to a colleague — *"when someone leaves, confirm the last
working day with HR, disable their Okta account, archive their Slack channels, and tell the manager
when it's done"*. The skill turns that into a playbook: ordered prose where every step that must
**call something** is marked with a `#Action` heading, and everything else stays as the instructions
a human (or the interpreter) reads.

```markdown
Title: Employee Offboarding
Trigger: A manager or HR reports that an employee is leaving, with a last working day.

Instructions:
1. #Lookup Users on the departing employee with includeManager to confirm identity and manager.
2. #Request Approval from HR to confirm the last working day.
3. #Deactivate User in Okta, then #Archive Channel for each private channel they owned.
4. #Send Direct Message to the manager confirming what was revoked.
```

That `#Action` marker is the whole point: it is what the runtime binds to a real function. At run
time a bound action calls its MCP tool; an unbound one hands off to a human instead of guessing.

Two kinds of action exist:

- **Native verbs** — the nine the interpreter implements itself: `#Send Direct Message`,
  `#Send Channel Message`, `#Send Email`, `#Leave Internal Note`, `#Resolve Request`,
  `#Escalate Request`, `#Request Approval`, `#Prompt for Handoff`, `#Trigger Form`. These always
  work; no binding needed.
- **Integration actions** — everything else (`#Deactivate User`, `#Archive Channel`,
  `#Get PTO Balance`), which must be matched to a tool on one of your MCP servers.

## How it finds the right function

There is no model guessing at this step — the matching is deterministic, in `scripts/create.py`.

`references/mcp-catalog.md` is generated by the app at startup and lists your live MCP servers
(headings) and their tools. Each `#Action` in the prose is tokenised, and every catalog tool is
scored against it:

| signal | points |
|---|---|
| a token of the **server** name appears in the action | **4** each |
| a token of the **tool** name appears in the action | **2** each |
| **every** tool token matched | **+1** |

The best-scoring tool wins if it reaches **4 or more** and nothing else ties it. Filler words
(`the`, `for`, `by`, `custom`, …) are ignored, so naming the server is optional: against a Slack
`archive_channel` tool, `#Archive Channel` scores 5 and `#Archive Slack Channel` scores 9 — both
bind, the second just more emphatically. Naming it helps only when two servers offer a similar
tool, where a tie leaves the action unbound on purpose rather than picking one at random.

This is why the skill names actions after the function rather than describing them: `#Get PTO
Balance` binds to a Workday `get_pto_balance` tool, while `#Check How Much Leave Is Left` scores
nothing and stays unbound. `create.py` prints each result as `BOUND`/`UNBOUND`, the model renames
what missed in at most two revisions, and anything still unbound is left deliberately — it becomes a
human hand-off at run time rather than a wrong call.

## Pipeline

model drafts JSON → `scripts/create.py` renders the canonical text, checks the action list and
auto-binds → the model fixes what the report flags (max two rounds) → `save_playbook_agent`
(browser client tool) creates the agent row.

- `references/syntax.md` — the syntax the app's `PlaybookDocument` parser accepts and the binding rule of `PlaybookAnalyzer`.
- `references/example-playbook-*.md` — the four playbooks from the workflow section, verbatim.
- `tests/` — `python3 -m unittest tests/test_create.py`
