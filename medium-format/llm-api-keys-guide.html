The Key Contract: Where LLM APIs Expect Your Credentials

Six major providers. Six slightly different conventions. A single misplaced header is all it takes for a 401. This is everything you need to know about authenticating against OpenAI, Claude, Grok, Gemini, DeepSeek, and Kimi.

The Orchestration Layer · April 2026 · 18 min read

Every request you send to a large language model carries two things: the content — the messages, the system prompt, the parameters — and the credential that proves you are allowed to send it at all. That credential, the API key, must be placed in precisely the right location or the server will reject the call before it reads a single token of your prompt. The location is not universal. Each provider made independent decisions about where keys belong, what the header should be named, and whether any companion headers are also required. Getting this wrong does not produce a helpful error message. It produces a 401, a vague authentication failure, and an afternoon of confusion.

This article documents the authentication conventions for six major LLM providers — OpenAI, Anthropic (Claude), xAI (Grok), Google (Gemini), DeepSeek, and Moonshot AI (Kimi) — with complete, working request examples for each. We also cover where keys should never be placed, how to handle them safely in production, and the patterns that apply uniformly across all providers regardless of their individual conventions.

· · ·

The Anatomy of an HTTP Request

Before looking at individual providers, it helps to understand the three places a credential could theoretically live in an HTTP request: the URL, the request body, or the headers. Each has different security properties, different visibility in logs, and different levels of support across providers.

Fig. 1 — The three places a key could go. Only headers are correct. URL params appear in server logs; body keys are logged by middleware.
The golden rule of API key placement

Always use HTTP headers. Never embed an API key in a URL query parameter — it will appear in server access logs, browser history, and any proxy layer in between. Never embed it in the request body — application logging middleware often captures the raw payload.

Headers are transmitted over the encrypted TLS channel and are not retained by standard web server access logs. They are the only safe location for a credential in an HTTP request.

The Provider Comparison at a Glance

Authentication Header Conventions — Six Major Providers

OpenAI Authorization Bearer sk-… Content-Type only
Anthropic (Claude) x-api-key sk-ant-… anthropic-version required
xAI (Grok) Authorization Bearer xai-… Content-Type only
Google (Gemini) x-goog-api-key AIza… Or as URL param (alt method)
DeepSeek Authorization Bearer sk-… Content-Type only
Kimi (Moonshot) Authorization Bearer sk-… Content-Type only

Two patterns immediately emerge. Most providers — xAI, DeepSeek, Kimi, and OpenAI — follow the standard OAuth2 Bearer token convention in the Authorization header. Anthropic uses a custom x-api-key header and additionally requires an anthropic-version header on every request. Google takes a third path, preferring a proprietary x-goog-api-key header while also supporting a URL parameter as a fallback (which you should avoid in production for the logging reasons described above).

"The header name is the contract. One wrong character and the server rejects the request before a single token of your prompt is ever read."

Provider by Provider: Complete Examples

GPT
OpenAI
gpt-4o · gpt-4-turbo · api.openai.com

OpenAI uses the industry-standard Bearer token pattern. Your key goes in the Authorization header prefixed with the literal string Bearer (note the trailing space). Keys begin with sk- and are obtained from the OpenAI platform dashboard.

openai · javascript fetch
// OpenAI — Authorization: Bearer sk-...

const response = await fetch("https://api.openai.com/v1/chat/completions", {
  method: "POST",
  headers: {
    "Authorization": `Bearer ${process.env.OPENAI_API_KEY}`,  // ← Bearer token
    "Content-Type": "application/json"
  },
  body: JSON.stringify({
    model: "gpt-4o",
    max_tokens: 1024,
    messages: [
      { role: "system", content: "You are a helpful assistant." },
      { role: "user",   content: "Explain vector databases in one paragraph." }
    ]
  })
});

const data = await response.json();
console.log(data.choices[0].message.content);
ANT
Anthropic — Claude
claude-sonnet-4 · claude-opus-4 · api.anthropic.com

Anthropic is the one provider that does not use the Authorization header. Instead it expects a custom x-api-key header. Additionally, every request must include an anthropic-version header specifying the API version string — omitting it produces a 400, not a 401, which makes it easy to misdiagnose.

anthropic · javascript fetch
// Anthropic — x-api-key + anthropic-version (both required)

const response = await fetch("https://api.anthropic.com/v1/messages", {
  method: "POST",
  headers: {
    "x-api-key":        `${process.env.ANTHROPIC_API_KEY}`,  // ← custom header, no "Bearer"
    "anthropic-version": "2023-06-01",                        // ← required companion header
    "Content-Type":     "application/json"
  },
  body: JSON.stringify({
    model: "claude-sonnet-4-20250514",
    max_tokens: 1024,
    system: "You are a helpful assistant.",
    messages: [
      { role: "user", content: "Explain vector databases in one paragraph." }
    ]
  })
});

const data = await response.json();
console.log(data.content[0].text);  // note: different response shape than OpenAI
XAI
xAI — Grok
grok-3 · grok-3-mini · api.x.ai

xAI's Grok API is OpenAI-compatible, meaning it follows the same Bearer token convention and exposes an endpoint structure nearly identical to OpenAI's. This means you can often swap the base URL and API key in existing OpenAI integrations with minimal code changes. Keys begin with xai-.

const response = await fetch("https://api.x.ai/v1/chat/completions", {
  method: "POST",
  headers: {
    "Authorization": `Bearer ${process.env.XAI_API_KEY}`,  // ← same as OpenAI
    "Content-Type":  "application/json"
  },
  body: JSON.stringify({
    model: "grok-3",
    max_tokens: 1024,
    messages: [
      { role: "system", content: "You are a helpful assistant." },
      { role: "user",   content: "Explain vector databases in one paragraph." }
    ]
  })
});

const data = await response.json();
console.log(data.choices[0].message.content);
GEM
Google — Gemini
gemini-2.0-flash · generativelanguage.googleapis.com

Google Gemini uses a proprietary header, x-goog-api-key, and a different endpoint structure than the other providers. The URL encodes the model name and the action (generateContent), and messages use a parts array inside contents rather than a flat messages array. Keys begin with AIza.

gemini · javascript fetch
// Gemini — x-goog-api-key header + different URL/body structure

const model = "gemini-2.0-flash";
const url   = `https://generativelanguage.googleapis.com/v1beta/models/${model}:generateContent`;

const response = await fetch(url, {
  method: "POST",
  headers: {
    "x-goog-api-key": `${process.env.GEMINI_API_KEY}`,  // ← Google's custom header
    "Content-Type":   "application/json"
  },
  body: JSON.stringify({
    systemInstruction: {           // system prompt goes here, not in messages
      parts: [{ text: "You are a helpful assistant." }]
    },
    contents: [{                    // "messages" equivalent
      role: "user",
      parts: [{ text: "Explain vector databases in one paragraph." }]
    }],
    generationConfig: { maxOutputTokens: 1024 }
  })
});

const data = await response.json();
console.log(data.candidates[0].content.parts[0].text);

Building a Unified Provider Client

Because four of the six providers share the OpenAI message schema, you can build a thin abstraction that normalises the differences and lets you swap providers with a single environment variable. The key insight is to isolate the two things that vary per provider: the base URL and the headers function.

unified client · javascript
// A minimal unified client for all six providers

const PROVIDERS = {

  openai: {
    url:     "https://api.openai.com/v1/chat/completions",
    headers: (key) => ({
      "Authorization": `Bearer ${key}`,
      "Content-Type":  "application/json"
    }),
    model:   "gpt-4o"
  },

  anthropic: {
    url:     "https://api.anthropic.com/v1/messages",
    headers: (key) => ({
      "x-api-key":        key,
      "anthropic-version": "2023-06-01",     // unique to Anthropic
      "Content-Type":     "application/json"
    }),
    model:   "claude-sonnet-4-20250514"
  },

  grok: {
    url:     "https://api.x.ai/v1/chat/completions",
    headers: (key) => ({
      "Authorization": `Bearer ${key}`,
      "Content-Type":  "application/json"
    }),
    model:   "grok-3"
  },

  deepseek: {
    url:     "https://api.deepseek.com/chat/completions",
    headers: (key) => ({
      "Authorization": `Bearer ${key}`,
      "Content-Type":  "application/json"
    }),
    model:   "deepseek-chat"
  },

  kimi: {
    url:     "https://api.moonshot.cn/v1/chat/completions",
    headers: (key) => ({
      "Authorization": `Bearer ${key}`,
      "Content-Type":  "application/json"
    }),
    model:   "moonshot-v1-8k"
  }

};

async function chat(providerName, apiKey, userMessage, systemPrompt = "") {
  const p = PROVIDERS[providerName];

  // Anthropic uses a different request schema
  const body = providerName === "anthropic"
    ? { model: p.model, max_tokens: 1024, system: systemPrompt,
        messages: [{ role: "user", content: userMessage }] }
    : { model: p.model, max_tokens: 1024,
        messages: [
          { role: "system", content: systemPrompt },
          { role: "user",   content: userMessage }
        ] };

  const res  = await fetch(p.url, {
    method:  "POST",
    headers: p.headers(apiKey),
    body:    JSON.stringify(body)
  });

  const data = await res.json();

  // Normalise the response shape
  return providerName === "anthropic"
    ? data.content[0].text
    : data.choices[0].message.content;
}

// Usage — swap the first argument to change provider
const answer = await chat("anthropic", process.env.ANTHROPIC_API_KEY,
  "Explain vector databases in one paragraph.",
  "You are a helpful assistant."
);
console.log(answer);

Keeping Keys Safe in Production

Authentication conventions are only half the story. The other half is ensuring keys never escape into places where they can be read by unintended parties. A key placed correctly in a header is still compromised if it ends up in a commit, a client-side bundle, or a CI log.

Fig. 2 — Safe vs. unsafe paths for API keys. Any path that touches a client bundle, a log file, or version control is a leak waiting to happen.

The backend proxy pattern

For web applications, the correct pattern is always to call LLM APIs from your backend, never from the browser. Your server holds the key in an environment variable, proxies requests from the frontend, and adds the credential at the server layer — where the client never sees it. This applies regardless of which provider you use.

backend proxy · node / express
// server.js — the key lives here, never in the browser
import express from "express";
import "dotenv/config";

const app = express();
app.use(express.json());

app.post("/api/chat", async (req, res) => {
  const { message } = req.body;

  // Key read from env — never exposed to client
  const response = await fetch("https://api.anthropic.com/v1/messages", {
    method: "POST",
    headers: {
      "x-api-key":        process.env.ANTHROPIC_API_KEY,  // ← from .env, not client
      "anthropic-version": "2023-06-01",
      "Content-Type":     "application/json"
    },
    body: JSON.stringify({
      model: "claude-sonnet-4-20250514",
      max_tokens: 1024,
      messages: [{ role: "user", content: message }]
    })
  });

  const data = await response.json();
  // Return only the text — never forward the raw provider response
  res.json({ reply: data.content[0].text });
});

app.listen(3000);

Conclusion: One Key, One Header, One Rule

The authentication landscape across LLM providers is simpler than it first appears. Four of the six major providers — OpenAI, Grok, DeepSeek, and Kimi — use the identical Bearer token convention inherited from OAuth2. Google uses a proprietary header name but the same underlying concept. Only Anthropic breaks from the pack entirely, with a custom header name and a required versioning companion.

The deeper rule is not about which header to use — it is about where the call happens. API keys belong in server-side environment variables, read at runtime, injected into request headers by backend code that the client never touches. Any other pattern is a credential leak in waiting. The header is the mechanism; the server boundary is the guarantee.

As the number of providers in a project grows — and it will grow — a thin normalisation layer like the unified client shown above pays for itself immediately. The provider changes; the header function changes; the rest of your code does not.
