System Architecture — Persistent Memory for AI Chat

Stateful Chat: How an AI Learns to Remember You

A technical walkthrough of a two-scope persistent memory system — USER preferences, MEMORY context, a two-stage LLM extractor with semantic deduplication, and a post-response trigger that keeps latency at zero.

The Memory Layer · April 2026 · 12 min read

I wanted my AI assistant to remember me. Not in a creepy way — just to stop starting every conversation from scratch, to stop repeating my stack, my language preferences, the architecture decisions I had already walked through three weeks ago. After a few long sessions of back-and-forth with Claude — some of them genuinely arguments — we landed on an algorithm that makes smart decisions about what to keep, what to throw away, and how to store it. Here is how we did it.

The problem, stated generically: chat with a large language model is, by default, amnesiac. Every new conversation starts from zero. The model does not know whether you are a senior engineer who wants the short answer or a beginner who needs the scaffolding, whether you type in French or English, whether the project you are building runs on PostgreSQL or MongoDB, whether last week you already decided to migrate your auth stack from FreeIPA to Authentik. You tell it, it helps, then the memory evaporates.

The brute-force fix — dump every past chat into the next prompt — does not scale. Token cost grows linearly with conversation history, irrelevant context pollutes the signal, and retrieval quality actually gets worse as the blob gets bigger. The better fix is selective, structured persistence: extract only what matters, separate by scope, deduplicate ruthlessly, inject it back into future contexts. What follows is what we built.

· · ·

Two Scopes, Not One

The core design choice is the separation of memory into two distinct scopes. This is not cosmetic. The scopes change at different rates, serve different purposes, and require different classification logic.

USER holds identity and communication preferences. This is the who of the conversation: biographical facts, language preferences, tone preferences, location, professional role. It rarely changes. Examples:

USER — Examples

· Francophone, based in Saint-Jérôme, Québec.

· Prefers concise answers with minimal preamble.

· Uses English for technical discussions, French for conversational ones.

· Works as an infrastructure architect specializing in on-premise AI.

MEMORY holds working context. This is the what of the user’s ongoing work: codebases, stacks, architectural decisions, domain facts, active projects. It changes constantly:

MEMORY — Examples

· Building a PHP 8.3 / Symfony application with PostgreSQL 16 + pgvector.

· Uses OpenBao for secrets management, Forgejo for git hosting.

· Decided on 2026-03-15 to migrate the auth system from FreeIPA to Authentik.

· Deployment target: Proxmox cluster with TrueNAS iSCSI storage.

Three reasons the split matters. First, USER facts compound slowly over months while MEMORY facts churn week to week — so different compaction strategies apply. Second, they serve different purposes downstream. USER informs how the model speaks; MEMORY informs what the model knows. Clean separation lets you inject them into distinct parts of the system prompt and reason about them independently. Third, it makes classification tractable. Asking an LLM "is this worth remembering?" is vague. Asking "is this a fact about who the user is, or about what they are currently working on?" has a clear answer.

The Turn Lifecycle

Every chat turn runs through the same loop. Before the turn begins, the current USER and MEMORY blocks are pulled from the user_memories table and injected into the system prompt. The model sees them as context for the assistant’s response. After the response has streamed, extraction runs in the tail of the PHP process, invisible to the user. Here is the full flow:

Fig. 1 — The turn lifecycle. Steps 1–4 are user-facing. Steps 5–8 run post-response, invisibly.

Two architectural choices in that diagram carry most of the system’s weight. The two-stage extractor (steps 6 and 7) is what keeps memory clean. The shutdown-hook trigger (steps 4 and 5) is what keeps latency at zero. We will take them in turn.

· · ·

Stage 1: The Proposal

After the response flushes, an extraction LLM call runs. By default this is Claude Haiku 4.5 — cheap, fast, and accurate enough for the task. The user can configure a different model if they want to trade cost for quality, but Haiku is the right default: extraction is a well-defined classification task, not an open-ended reasoning one, and a larger model buys little.

The extractor sees exactly four things: the current USER block, the current MEMORY block, the last user message, and the last assistant reply. It proposes additions in a strict structured format:

JSON — Stage 1 output 
{
  "user_additions": [
    "Prefers French for conversational questions, English for technical ones"
  ],
  "memory_additions": [
    "Uses register_shutdown_function + fastcgi_finish_request for"
    "post-response background extraction"
  ],
  "reason": "User explained their memory system architecture in the last"
            "turn; language preference inferred from mid-chat switch to French."
}

The reason field is not used by the system downstream. It exists for humans — it surfaces in the UI when a user inspects their memory history and asks “why does the AI think I prefer short answers?” The reason is the answer. It also serves as a debugging aid during development: when classifications go wrong, the reason usually reveals the misreading.

· · ·

Stage 2: The Semantic Guard

A single-stage extractor has a slow failure mode: paraphrase drift. Over enough turns, it will propose variations of the same fact:

The Paraphrase Problem

Turn 3 — “Prefers concise answers”

Turn 12 — “Likes short replies”

Turn 27 — “Wants brief responses”

Turn 44 — “Values compactness in communication”

Without a guard, all four get stored. The memory balloons with noise, and the next Stage 1 call sees an even longer USER block that generates even more paraphrase proposals. Memory entropy rises every turn.

Stage 2 is a second LLM call whose only job is to compare each proposed addition against the existing scope and reject near-paraphrases. The prompt calibrates the cutoff with explicit examples — without them, Haiku is either too permissive (everything looks different enough) or too strict (everything looks similar enough):

Stage 2 — Calibration Examples in the Prompt
Existing memory Proposed addition Verdict Why
Prefers concise answers Likes short replies REJECT Same meaning, different words
Uses PostgreSQL 16 Postgres 16 with pgvector extension KEEP Adds new info (pgvector)
Francophone in Québec Lives in Saint-Jérôme, Québec KEEP Refines location to a city
Uses Docker for containers Uses containers for deployment REJECT Weaker restatement of same fact
Deploys on Proxmox Proxmox cluster runs with TrueNAS iSCSI KEEP Adds storage configuration

The guard is deliberately conservative: when uncertain, it rejects. The cost asymmetry favors this. A false rejection costs little — if the fact is real, it will be proposed again on a future turn. A false acceptance costs much more — memory noise accumulates permanently until compaction or manual cleanup.

Zero-Latency Extraction

The most architecturally interesting part of the system is not the LLM calls — it is when they run.

Running extraction on the request’s critical path would add hundreds of milliseconds to every turn, even with a fast model. For interactive chat, that is unacceptable. The obvious alternative is a proper background job — a queue, a worker pool, a message bus. That works, but adds infrastructure the system does not otherwise need.

PHP offers a middle path that is almost unreasonably clean for this use case. The combination of fastcgi_finish_request() and register_shutdown_function() lets the process keep executing after the HTTP response has been delivered to the client. The user’s browser sees the response complete; the PHP process continues running; extraction happens in the tail.

PHP — Post-response extraction pattern 
// Register the extraction to run during shutdown.
// It captures the chat context by reference so it has
// everything it needs when the hook fires.
register_shutdown_function(function () use ($chatContext) {
    $this->memoryExtractor->extractAndStore($chatContext);
});

// Stream the assistant's response to the user.
$this->streamResponse($response);

// Flush output buffer and close the FastCGI connection.
// From this line on, the user has their answer. The page
// is interactive. They have moved on with their day.
fastcgi_finish_request();

// Execution continues. When this function returns,
// PHP calls the shutdown hook registered above.
// Stage 1 + Stage 2 run here, invisibly.

From the user’s perspective, latency is identical to a chat with no memory system at all. The response arrives, the page is interactive, extraction happens in the dark. No queue worker, no Redis-backed job broker, no sidecar process.

The Honest Caveat

This pattern is PHP-specific. Technically it is FastCGI-specific — PHP-FPM supports it, but PHP run as a CLI script or under mod_php does not. A Node.js or Python equivalent needs either fire-and-forget async (risky, can lose work if the process recycles) or a proper background queue (more infrastructure). If you are porting this design to another stack, the two-stage extraction and scope split translate cleanly; the zero-latency trick does not.

“The trick is not running extraction faster. It is running it after the user has already left.”

— The engineering heuristic behind the whole design

The Classification Rule That Exists Because of a Bug

Running Stage 1 at volume reveals a failure mode obvious in hindsight: the extractor drifts toward pattern-matching its own history.

Early in development, Haiku 4.5 would see that the last several biographical facts had been classified as USER and the last several project facts had been classified as MEMORY. So far so good. But when a new fact arrived that was genuinely biographical — “I work at a consulting firm” — Haiku would sometimes drop it into MEMORY because the last handful of classifications had been project-related. It was not reasoning about the nature of the fact; it was pattern-matching the recent output.

The fix is a hard rule restated at the top of the extraction prompt, then again with examples:

Hard Rule in the Extraction Prompt

Classify by nature, not by precedent.

· Biographical facts ALWAYS go to USER, never MEMORY.

· Technical/project facts ALWAYS go to MEMORY, never USER.

· Where similar facts previously landed is irrelevant.

· If a fact concerns who the user is rather than what they do, it is USER, even if the last ten classifications were all MEMORY.

Worth generalizing. Any LLM-based classifier that sees its own past outputs in its context is vulnerable to this drift. The defense is not just better few-shot examples — it is explicit, rule-based statements in the prompt that outrank pattern-matching. When an LLM drifts toward majority-class predictions in your system, the answer is usually a hard rule, not more training data.

Compaction: When a Scope Gets Too Big

Each scope has a soft token budget — a cap on how much space it can consume in the system prompt. When USER or MEMORY grows past its budget, a compaction pass runs. Compaction is a third LLM call, also Haiku 4.5 by default. It takes the current scope as input and produces a rewritten, terser version. Facts are not dropped; they are merged and compressed.

// MEMORY scope, before compaction (840 tokens)

// Same scope, after compaction (320 tokens, zero facts lost)

  PHP-FPM behind nginx; Composer for deps, PHPUnit for tests

Compaction runs opportunistically, not on every turn — its cost is amortized across many turns. The trigger is typically a percentage-over-budget threshold. The compaction prompt explicitly forbids dropping information; it is allowed only to restructure and summarize. That constraint matters: without it, the model will happily “summarize” by deleting facts it deems less important, which is exactly the opposite of what a memory system should do.

Audit Log and Revert

Every write to user_memories produces a corresponding event in UserMemoryEventsRepository. The event captures what was added, what was removed, what was compacted, the exact turn that triggered it, and the reason field from Stage 1 (or “compaction” for compaction events).

This enables two UI features that matter more than they look:

History view. The user sees every change to their memory over time. What was added yesterday. What was merged last week. What the extractor inferred from a specific message. This makes the system legible — users can understand what the AI thinks it knows about them.

Revert. Any change can be rolled back. If the extractor misclassifies a fact, if compaction over-compresses, if the user simply disagrees with what was stored, they can restore the prior state.

The audit log is not optional. LLM-based extraction will get things wrong — this is not a hypothetical, it is a statistical certainty at scale. An auditable, revertible memory system is what turns that failure mode from catastrophic (silent corruption of user context) into recoverable (visible event, one-click undo). Every memory system that writes without this capability is one extractor mistake away from a trust-destroying bug.

· · ·

Chat Only: Why Workflows Are Skipped

Workflows — pre-authored task runners executed with structured inputs — are deliberately excluded from memory extraction.

The reasoning: workflows do not reveal user preferences. A workflow invocation is a programmatic call, not a conversation. The user did not type anything conversational; they triggered a task with specific parameters. There is nothing biographical to learn, no communication preference to infer, no new context about ongoing work that is not already captured elsewhere. Running extraction on workflow turns would cost another Haiku call per run and produce noise — the extractor would hallucinate “memories” out of parameter names.

Skipping workflows is a clean, free win. Worth watching for equivalents in any memory system: if a turn type does not carry user signal, do not waste an extractor on it.

What This Design Gets Right

The memory system described here is not novel in any individual component. Two-scope classification, semantic deduplication, post-response extraction, audit logs — each exists elsewhere. What is unusual is the combination and the disciplined application of each piece. A few principles worth carrying forward:

Scopes are cheap; classification is expensive. Splitting memory into USER and MEMORY costs almost nothing in storage but buys significant clarity at extraction time. When the classification question is clear, the LLM gets it right more often. When it is ambiguous, no amount of prompt engineering saves you.

Two cheap LLM calls beat one expensive one. Running Haiku twice (proposal + guard) is faster and costs less than running Sonnet once, and the semantic guard catches a failure mode — paraphrase drift — that a single-stage call cannot. Staging is the feature.

Reliability comes from reversibility, not perfection. The audit log is not a nice-to-have. It is the load-bearing wall that lets the system ship with an imperfect extractor. Every memory system eventually stores something wrong; only the ones with revert survive the consequences.

Latency you cannot measure does not exist. The fastcgi_finish_request trick is the single cleanest piece of engineering in the system. It moves work out of the user’s critical path without adding infrastructure. When a pattern like this exists in your stack, use it before you reach for a queue.
